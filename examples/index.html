WebAssembly (CPU) vs. WebGL (GPU) Skinning Pipelines for the SMPL Avatar Model

Introduction

Deploying real-time human avatar capture and 3D rendering applications traditionally involves a heavy Python-based machine learning stack. Frameworks like PyTorch, JAX, and CUDA are ubiquitous in research, but they introduce major friction for client-side deployment, particularly in real-time browser environments.

The workstation-grade workstation runtime h3d.cpp consolidation bypasses this Python dependency using a native C++ engine. However, bringing these avatars to client-side browsers for interactive applications introduces a different systems challenge: how to evaluate 3D parametric human body models like SMPL (Skinned Multi-Person Linear model) within the strict compute and sandbox constraints of the web browser.

This systems-level study evaluates two distinct web architectures implemented in h3d.cpp's web frontend (smpl-web): a high-performance C++ WebAssembly (WASM) CPU engine, and an optimized WebGL (GPU) backend utilizing custom Three.js GLSL shaders to offload vertex deformations entirely to the GPU. We analyze the architectural trade-offs, memory copy overhead, and execution times of both pipelines.

The Mathematical Foundation of SMPL

To build and profile the rendering pipelines, we must first look at the mathematical formulations that define the shape and posture of the SMPL model. SMPL represents a human body as a template mesh T \in \mathbb{R}^{N \times 3} containing N = 6890 vertices, controlled by shape parameters \beta \in \mathbb{R}^{10} (the principal components of body shape variation) and pose parameters \theta \in \mathbb{R}^{72} (representing 24 joints in axis-angle format).

The vertex transformation pipeline proceeds through four main mathematical steps:

1. Shape Blend Shapes

The shape parameters \beta scale predefined directions of body variation (e.g., height, weight, proportions) to deform the template mesh:

T_s(\beta) = T_{template} + B_S(\beta)

where B_S(\beta) = \sum_{k=1}^{10} \beta_k S_k is the shape deformation vector, and S_k \in \mathbb{R}^{6890 \times 3} represent the shape principal component displacements. On the CPU, this is mapped as flat float arrays of shape (6890, 3, 10), accessed with strided strides of v \times 30 + k \times 3 + \text{axis}.

2. Pose Blend Shapes

To avoid artifacts like the "collapsing elbow" during joint rotations, SMPL adds pose-dependent dynamic offsets before skinning:

T_p(\theta, \beta) = T_s(\beta) + B_P(\theta)

where B_P(\theta) = \sum_{n=1}^{207} (R_n(\theta) - R_n(\theta^*)) P_n is the pose-corrective offset vector, R_n(\theta) represents the local rotation matrix of joint n, and P_n \in \mathbb{R}^{6890 \times 3} represents the pose-corrective displacements. The pose feature vector is computed by taking the local rotation matrices of the 23 active joints (excluding the global root orientation) in SO(3) and subtracting the identity matrix I (yielding a 207-dimensional vector: 23 \text{ joints} \times 9 \text{ matrix elements}).

3. Joint Regression

The 3D locations of the 24 joints J(\beta) are regressed from the shaped mesh template:

J(\beta) = \mathcal{J} T_s(\beta)

where \mathcal{J} \in \mathbb{R}^{24 \times 6890} is a sparse regressor matrix learned from data. For performance, rather than doing dense matrix multiplication, we perform sparse accumulation by looping only over non-zero weights in the pre-computed sparse index tables.

4. Linear Blend Skinning (LBS)

Finally, the posed vertices are mapped to their world coordinates using joint transformations recursively computed along the kinematic tree:

v_i' = \sum_{j=1}^{24} w_{i, j} G_j(\theta, J(\beta)) G_{j, \text{rest}}^{-1} v_{i, \text{posed}}

where w_{i, j} is the skinning weight defining the influence of joint j on vertex i, G_j(\theta, J(\beta)) \in \mathbb{R}^{4 \times 4} is the global transformation matrix of joint j computed by Forward Kinematics (FK), and G_{j, \text{rest}}^{-1} is the inverse rest pose transform which moves the rest-pose vertex back to the bone's local space before applying the posed transformation.

Linear Blend Skinning Constraints
Each vertex in the SMPL model is typically influenced by multiple bones. To perform LBS efficiently, we restrict the influence to the top 4 most dominant joints per vertex and normalize their weights to sum to 1.0. This matches the native constraints of GPU hardware skinning engines.

Two Rendering Philosophies on the Web

To implement these equations in a web browser, h3d.cpp provides two architectures inside the interactive viewer:

Pipeline A: WASM CPU Engine

This engine compiles the C++ SMPL implementation directly to WebAssembly using Emscripten with optimization flags (-O3 -msimd128). All mathematical steps—including Rodrigues rotations, Shape/Pose Blend Shapes, Forward Kinematics, LBS, and Vertex Normal cross-products—are executed in C++ on the CPU.

The JavaScript wrapper passes parameters by copying values into the WASM heap virtual memory space and directly reads completed, fully-skinned vertices and normals from heap pointers to update Three.js Vertex Buffer Objects (VBOs).

Pipeline B: WebGL(GPU)

This pipeline offloads the expensive vertex deformation mathematics entirely to the GPU's vertex shaders via custom WebGL modifications, bypassing WebAssembly.

During initialization, the full displacement tables for shape and pose variations are packed into 2D floating-point textures. On each frame, the CPU (running JavaScript) only handles lightweight tasks: converting joint orientations into quaternions for the skeleton, computing the 207-dimensional pose feature vector, and regressing joints (only when shape parameters change). The vertex shader fetches the displacements from the textures, deforms the base template, and executes Linear Blend Skinning (LBS) in parallel.

Performance Analysis

To evaluate the execution efficiency of the WASM CPU and WebGL(GPU) backends, the web viewer runs a standardized benchmark suite directly in the browser. Measuring raw frame time (the total duration of the render loop tick) is handled via performance.now(). However, because WebGL drawing commands are executed asynchronously by the GPU, CPU-side timers cannot measure hardware execution directly.

To obtain precise measurements of actual GPU hardware execution time, the benchmark suite utilizes the WebGL Disjoint Timer Query Extension (EXT_disjoint_timer_query_webgl2 or its WebGL 1 fallback). This allows the application to query the GPU for the precise elapsed time spent processing drawing calls, independent of browser garbage collection, page layout reflows, or scheduling delays.

Asynchronous GPU Profiling Workflow

Because WebGL drawing commands are sent to the GPU queue asynchronously, measuring their duration requires a deferred query loop:

  1. Begin Query: A query object is created and begun using gl.beginQuery(extTimerQuery.TIME_ELAPSED_EXT, query) immediately before drawing.
  2. End Query: The query is stopped with gl.endQuery() right after the Three.js renderer.render() call.
  3. Enqueue: The query object is placed into a query queue.
  4. Poll and Resolve: On subsequent frames, the application polls the query status via gl.getQueryParameter(query, gl.QUERY_RESULT_AVAILABLE). Once available, the GPU time is fetched via gl.getQueryParameter(query, gl.QUERY_RESULT) and converted from nanoseconds to milliseconds, while the query object is deleted.

By combining WebGL disjoint queries with internal C++ high-resolution timers exposed through WASM bindings (e.g., getShapeTime(), getPoseTime(), getSkinningTime()), we receive a complete breakdown of the execution costs across every stage of the animation pipeline.

Architectural and Qualitative Comparison

The table below outlines the core architectural differences and qualitative technical trade-offs between the WebAssembly CPU and WebGL(GPU) engines:

Evaluation Category Pipeline A: WASM CPU Engine Pipeline B: WebGL(GPU)
Math Execution Entirely on CPU (compiled C++). CPU (JS): Joint regression & pose features; GPU (Shaders): Shape blend, pose correctives, and skinning.
CPU-to-GPU Upload High: Uploads 6890 \times 3 coordinates and 6890 \times 3 normals every frame. Low: Uploads skeleton matrices (24 \times 16 floats) and uniforms (betas and pose features) every frame. Base positions remain completely static.
Performance (FPS) Bound by CPU compute power and JS-WASM serialization. Typically slower for active sequences. Highly performant (solid 60 FPS) due to parallel GPU vertex transformation.
Multi-Avatar Scalability Poor: Evaluating multiple characters quickly consumes CPU core cycles. Excellent: Multiple instances reuse static VBOs and execute shaders in parallel.
Codebase Synchronization Perfect: Shares the exact C++ source code from h3d.cpp via bindings. Duplicate: Requires maintaining separate JavaScript ports of joint regression and pose features.
Pose Correctives Impact Low impact (evaluated in highly optimized C++ loops). Low-Medium impact: Computed entirely on the GPU via texture lookups, but requires binding and uploading the 207-dimensional pose feature vector every frame.

The Phase 1 profile reveals that:

  • WASM (CPU) - Case 1: Delivers highly efficient, vectorized mathematical execution, completing the entire SMPL equation (including Linear Blend Skinning and normal estimation) in 4.131 ms on the CPU. The JS-WASM data boundary copy overhead is negligible (0.029 ms).
  • WebGL (GPU) + Correctives - Case 2 (Hybrid Baseline): Serves as our initial baseline benchmark. It exhibits a high frame time of 7.780 ms, which is heavily dominated by a 7.455 ms CPU overhead in JavaScript. The major bottleneck here is that the pose correctives, Shape Blend Shapes, and Pose Blend Shapes calculations—all of which are highly compute-intensive—are currently executing on the JS CPU. This CPU-side computation of the 207-dimensional pose feature vector (4.408 ms) and subsequent uniform binding is the primary driver of latency in the WebGL(GPU) pipeline, representing a clear target for future shader-based optimization passes.

Phase 2: Fully Offloaded GPU Shader Pipeline (Optimized)

In this optimized phase, we move the compute-intensive Pose Correctives, Shape Blend, and Pose Blend calculations entirely to the GPU vertex shader. Floating-point data textures containing the displacement tables are pre-loaded to GPU VRAM, and the shader reads offsets in parallel using texelFetch.

The Phase 2 profile demonstrates a massive performance breakthrough:

  • WebGL (GPU) - Fully Offloaded: The CPU loop duration drops to an astonishing 0.461 ms, yielding a theoretical throughput of over 2100 frames per second.   • GPU Query Verification: The GPU disjoint timer queries report an active GPU workload of 2.523 ms, demonstrating that the GPU easily absorbs the parallel blendshape texture fetches without bottlenecks, confirming the efficiency of the offloaded approach.

Memory and Bandwidth Overhead

The main bottleneck of Pipeline A is the memory bandwidth between the WebAssembly memory heap (HEAPF64) and WebGL. Because Emscripten works within its own isolated memory space, the calculated floating-point coordinates must be copied into a JavaScript typed array before they can be uploaded to the GPU's Vertex Buffer Objects (VBOs).

In code, this data copying is visible in smpl-web/src/main.js:

// 1. Retrieve raw pointers from WASM Memory space const ptr = smplRuntime.getVerticesPtr(); const numVertices = smplRuntime.getVerticesSize(); // 2. Instantiate Float64 views directly on Emscripten's Heap const wasmBufferView = new Float64Array( h3d.HEAPF64.buffer, ptr, numVertices * 3 ); // 3. Copy vertex data from WASM heap to JS Three.js buffer positions.set(wasmBufferView); state.geometry.attributes.position.needsUpdate = true;

This process generates substantial serialization overhead when running animations at 30 or 60 frames per second. Conversely, Pipeline B avoids per-frame mesh uploads. Once the base shape is configured (calculated when \beta changes), the mesh vertices remain static on the GPU. Only the 24 bone transformations (represented as 4 \times 4 matrices or quaternions) are uploaded to WebGL uniforms on each frame:

// Update bone rotations on CPU in JS const axis = new THREE.Vector3(); for (let i = 0; i < 24; i++) { const rx = pose[i * 3 + 0]; const ry = pose[i * 3 + 1]; const rz = pose[i * 3 + 2]; const theta = Math.sqrt(rx * rx + ry * ry + rz * rz); if (theta < 1e-8) { bones[i].quaternion.set(0, 0, 0, 1); } else { axis.set(rx / theta, ry / theta, rz / theta); bones[i].quaternion.setFromAxisAngle(axis, theta); } } // SkinnedMesh automatically updates uniform arrays for GPU skinning

WebGL GPU Texture-Based Displacement

To perform shape blending (B_S) and pose correctives (B_P) on the GPU without uploading massive vertex displacement arrays every frame, the WebGL(GPU) backend packs the SMPL model's deformation tables into 2D floating-point textures during initialization.

These textures are loaded once into GPU memory:

  • Shape Blends (u_shapedirsTexture): A 6890 \times 10 texture of type THREE.FloatType using the RGB format containing the principal displacements for the 10 shape components (extracted from shapedirs).
  • Pose Blends (u_posedirsTexture): A 6890 \times 207 texture of type THREE.FloatType containing the displacements for the 207 pose-corrective dimensions (extracted from posedirs).

Every frame, the CPU calculates the 207-dimensional pose feature vector in JavaScript and uploads it along with the 10 shape parameters as uniforms. In the custom vertex shader, the vertex index (a_vertexIndex) is used to perform exact texture lookups via texelFetch:

// Shape Blend offset accumulation int vi = int(a_vertexIndex); vec3 shapeOffset = vec3(0.0); for (int k = 0; k < 10; k++) { vec4 offset = texelFetch(u_shapedirsTexture, ivec2(vi, k), 0); shapeOffset += u_betas[k] * offset.xyz; } // Pose corrective offset accumulation (if enabled) vec3 poseOffset = vec3(0.0); if (u_enablePoseCorrectives > 0.5) { for (int m = 0; m < 207; m++) { vec4 offset = texelFetch(u_posedirsTexture, ivec2(vi, m), 0); poseOffset += u_poseFeature[m] * offset.xyz; } } // Apply displacement to base template position before skeleton skinning transformed += shapeOffset + poseOffset;

This architecture entirely bypasses WebAssembly for WebGL(GPU) mode. By executing the displacement accumulation in the vertex shader, the GPU takes advantage of its massive parallel hardware execution, leaving the CPU completely free of vertex-level loops.

Conclusion

The h3d.cpp project's exploration of web rendering techniques demonstrates that there is no one-size-fits-all solution for real-time character animation. WebAssembly provides a robust, zero-maintenance mechanism to share complex model math directly with high-performance desktop implementations, but faces scaling limits due to browser memory architectures and CPU-GPU bandwidth. Conversely, the WebGL(GPU) backend offers fluid performance for crowds and avatars, but requires careful CPU-GPU bandwidth management when active pose correctives require uploading vertex offsets every frame.
